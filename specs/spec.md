## 1. 目的・プロダクトビジョン

**「マッチングアプリの写真とメッセージを、"なぜ良いか"の根拠つきでAIが改善してくれる、伸びしろコーチアプリ」**

マッチングアプリ利用者の多くは「プロフィール写真の選び方」と「マッチ直後のメッセージ」でつまずく。既存の本体内蔵AI機能(タップル等)は文章生成に留まり、「どの写真が良いか・なぜ良いか」の根拠提示や、アプリ横断で使える改善支援は手薄である。

ノビシロは、ユーザー自身が素材(写真・会話スクショ)を持ち込み、AIが**理由付きで**判定・提案し、ユーザーが自分の手でマッチングアプリ側に反映する、という独立した支援アプリである。

- **長期ビジョン**: マッチング前〜結婚までの全フェーズを支援するエージェント体験。
- **v1.0**: マッチング前〜直後(写真選び+返信支援)に意図的に絞る。
- **やらないことによる価値**: 自動操作をせず(規約違反リスク回避)、実在の顔を再現する画像生成をしない(写真詐欺の助長回避)ことで、「信頼できるコーチ」というポジションを守る。

## 2. 対象ユーザー

- **主対象**: 日本国内のマッチングアプリ(Pairs / with / Omiai / タップル / Tinder 等)を利用中または利用開始しようとしている**18歳以上**の成人。
- 複数アプリを併用しており、アプリ本体の内蔵機能では横断的な改善ができない人。
- 「いいねが伸びない」「マッチしても会話が続かない」という課題を自覚しているが、人力添削サービス(数百〜数千円)に頼むほどの心理的・金銭的ハードルは越えたくない人。
- **非対象**: 未成年(オンボーディングで18歳以上確認を行い、対象外とする)。マッチングアプリの自動操作を求めるユーザー。

## 3. 主要な利用の流れ

### フローA: 写真判定(初回価値到達の基準)
1. アプリを開く →(初回のみ)オンボーディング+18歳以上確認
2. ホームから「写真をみてもらう」を選択
3. 端末の写真ライブラリから候補写真を1〜5枚選択して送信
4. **数十秒以内に判定結果が返る**: 推奨メイン写真の提示+各写真の理由付き評価+改善提案
5. (深掘り)改善提案に対応する**参考イメージ**(構図・光・ポーズの模式イラスト)を閲覧
6. ユーザーが自分でマッチングアプリ側の写真を差し替える

初回価値到達 = ステップ4(理由付き判定結果の表示)時点。参考イメージ(ステップ5)は初回価値到達の定義に含めない(research.md確定事項)。

### フローB: メッセージ返信支援
1. ホームから「返信を考えてもらう」を選択
2. 会話画面のスクリーンショットをアップロード、**または**相手のメッセージをテキストで貼り付け
3. トーン(丁寧/カジュアル/ユーモア)を任意選択
4. 返信案が3件、それぞれ短い狙いの説明付きで返る
5. ユーザーがコピーして自分でマッチングアプリ側に送信する

### フローC: 課金
- 無料枠(4章参照)を消費し切った状態で機能を実行しようとするとペイウォールを表示 → RevenueCat経由でサブスクリプション購入 → 無制限利用。

## 4. 核となる機能

| ID | 機能 | 概要 |
|---|---|---|
| F-1 | 写真判定 | 1〜5枚の写真をAI(vision対応LLM)が評価。推奨メイン写真+各写真の理由・改善提案を返す。根拠は公開調査・業界経験則に基づく一般的傾向として提示し、出典を誤認させない |
| F-2 | 参考イメージ表示 | 改善提案のカテゴリ(光・構図・表情・服装等)に対応する**アプリ同梱の静的参考イラスト**を表示。実在の顔を再現する画像生成は行わない |
| F-3 | メッセージ返信支援 | 会話スクショ(vision読み取り)またはテキスト貼り付けから、返信案3件を狙いの説明付きで生成 |
| F-4 | フリーミアム課金 | 無料枠: **写真判定 累計3回・返信案生成 累計5回**。以降は月額サブスクリプション(RevenueCat)で無制限。価格は仮に月額980円とし、App Store Connect設定時に decision-log 経由で最終確定 |
| F-5 | 履歴 | 過去の判定結果・返信案をAsyncStorageに保存し、オフラインでも閲覧可能 |
| F-6 | 計測・監視 | 成功指標イベントの記録(STEP 7レポート用)と、Sentryによるクラッシュ計測 |

### F-1/F-3の判定品質に関する設計原則
- フィードバックは**否定でなく改善提案の形**にする(user_wellbeing)。容姿を直接否定する表現の禁止語リストを設け、出力をフィルタする。
- 数値・統計に言及する場合は「一般的な傾向として」「◯◯社の公開調査によると」等、出典を誤認させない定型表現のみ許可する。「Pairsのデータによると」等、他社非公開データを想起させる表現は禁止。
- **体型・体重への直接的な言及は行わない**。改善提案は構図・光・表情・服装・背景等の撮影要素に限定し、人種・宗教・性的指向等の属性を推定・言及する表現も生成しない(vision LLM提供元のUsage Policy対応。decision-log.md DL-005参照)。
- **改善提案は「体型・体重そのものを変える」系の助言(例: 「体を鍛える」「痩せる」等)を一切行わない**。その代わり、次の4観点に特化した具体的で行動可能なアドバイスに限定する(いずれも体型そのものへの評価を含まない):
  - 構図・角度(例: 距離感、ポーズ、写る範囲)
  - 服装・スタイリング(例: 色、羽織り方、シルエットの見せ方)
  - 光・背景(例: 光源の向き、逆光の回避)
  - 表情(例: 目線、口角)

## 5. 今回やらないこと(v1.0スコープ外)

1. **マッチングアプリ本体機能**(ユーザー同士のマッチング・メッセージング・プロフィール公開)— 出会い系サイト規制法の対象化を避ける
2. **自動操作・自動投稿**(スワイプ・いいね・メッセージ送信の自動化、マッチングアプリとのAPI/画面連携)— Tinder等の規約違反リスク
3. **実在の顔を再現する画像生成**(ユーザーの顔写真をもとにした理想画像の生成)— 写真詐欺助長リスク
4. **画像生成APIによる参考イメージの動的生成** — v1.0は静的ライブラリ方式。動的生成は将来ロードマップ(下記)
5. **プロフィール文の添削・生成単体機能** — 本体内蔵機能とコモディティ競合するため主軸にしない
6. **デート打診・日程調整、交際後の関係相談、結婚支援** — 将来フェーズ
7. **ユーザー自己申告データ(いいね数・マッチ数)の蓄積・統計化** — 将来フェーズ(サーバーが必要になるため)
8. **ユーザー同士の添削結果共有** — 規制法の解釈を変えうるため明示的に除外
9. Android対応(v1.0はiOSのみ。EAS構成は将来のAndroid対応を妨げない形にする)

**将来ロードマップ(spec.mdには含めない、参考)**: 参考イメージの動的生成(画像生成API)、自己申告データによる自社統計、メッセージ支援の会話継続コーチング、Android版。

## 6. 技術的な前提・制約

- **クライアント**: React Native + Expo(マネージドワークフロー)、iOS先行
- **ローカル保存**: AsyncStorage(履歴・利用回数・設定)。写真そのものは端末ライブラリ参照のみで、アプリ独自の永続コピーは持たない
- **AI処理**: vision対応LLM API(Claude API想定)。**アプリからの直接呼び出しは行わず、軽量プロキシ(Cloudflare Workers等)経由とする**。APIキーはプロキシ側の環境変数にのみ置き、クライアントには一切埋め込まない
  - ⚠️ これはCLAUDE.md「サーバー不要のMVP基本」の**例外**。APIキー抽出リスク回避のためであり、decision-log.md DL-001 に記録済み(人間承認済み)
  - プロキシは**ステートレス**とする: 写真・会話内容をログ・ストレージに永続化しない(プライバシー申告と整合させる)
  - **レート制限(不正利用・コスト超過対策)**: プロキシ入口でリクエスト元IPアドレスを鍵とするレート制限を実施する。閾値は**1 IPアドレスあたり1時間20回・24時間100回**(F-1/F-3の判定・生成リクエスト合算。いずれか先に到達した方で制限)。超過時はHTTP 429を返しvision APIを呼び出さない(AC-023)。IPベースのため同一IP配下の複数端末(公衆Wi-Fi等)の正規利用を誤ってブロックしうる残存リスクがあり、decision-log.md DL-004に記録済み(人間承認済み)。デバイス単位の恒久対策(DeviceCheck/App Attest等)はv1.0スコープ外とする
  - **コンテンツモデレーションの実施主体**: プロキシ内で、vision LLM提供元(Claude API想定)が提供するコンテンツフィルタ/モデレーション機能を呼び出す。提供元側の機能だけでは不十分と判明した場合は、独立したモデレーションAPIをプロキシに追加選定する(AC-022)
  - **プロキシのリポジトリ・デプロイ**: プロキシは本アプリ(nobishiro-app)とは別リポジトリ(例: `nobishiro-proxy`)で管理し、Cloudflare Workersにデプロイする。AC-014の手動確認(ログ・永続化コードのレビュー)は当該リポジトリを対象に実施する
- **課金**: RevenueCat(業務フローv5のFlow 7に従う)
- **イベント計測**: PostHog(Flow 8に従う)。**匿名ID(端末生成のランダムID)のみを使用し、IDFA等の広告識別子・端末フィンガープリンティングは行わない**。この設計により、トラッキングに該当する識別子の取得・共有を行わないためApp Tracking Transparency(ATT)の許諾ダイアログは不要と判断する(根拠を審査メモに記載。DoD項目6)。クラッシュ計測: Sentry
- **ビルド・提出**: EAS Build / EAS Submit。シークレットはEAS Secrets管理
- **テスト**: unit = Jest、E2E = Maestro
- **依存ライブラリ**: 上記スタックの標準構成以外を追加する場合は事前承認必須(CLAUDE.md)
- **性能目標**: 写真判定・返信案生成とも、送信から結果表示まで通常回線(4G相当以上)で**30秒以内**。60秒でタイムアウトとしてエラー+再試行導線を出す
- **オフライン**: AI機能はオフライン時に実行不可(明示的なエラー表示)。履歴閲覧はオフライン可

## 7. データ構造(案)

すべてAsyncStorageに保存。キーは `nobishiro:` プレフィックスで統一。

```typescript
// nobishiro:profile
type Profile = {
  ageConfirmedAt: string | null; // ISO8601。18歳以上確認の完了日時
  onboardingCompletedAt: string | null;
};

// nobishiro:quota
type Quota = {
  photoAssessmentsUsed: number; // 累計。無料枠3
  replyGenerationsUsed: number; // 累計。無料枠5
};
// サブスク状態はRevenueCatのentitlement("pro")を都度参照し、ローカルには持たない

// nobishiro:assessments (配列、新しい順)
type PhotoAssessment = {
  id: string;            // uuid
  createdAt: string;
  photoRefs: string[];   // 端末ライブラリのasset ID(画像のコピーは保存しない)
  recommendedIndex: number; // 推奨メイン写真のインデックス
  results: {
    score: number;       // 1-5
    reasons: string[];   // 理由(良い点)
    improvements: {
      category: 'light' | 'composition' | 'expression' | 'outfit' | 'background' | 'other';
      advice: string;    // 改善提案(提案形の文言)
    }[];
  }[];
};

// nobishiro:replySessions (配列、新しい順)
type ReplySession = {
  id: string;
  createdAt: string;
  inputType: 'screenshot' | 'text';
  inputText: string;     // テキスト入力 or スクショから読み取った会話要約
  tone: 'polite' | 'casual' | 'humorous' | null;
  suggestions: { text: string; aim: string }[]; // 返信案3件+狙い
};

// 参考イメージライブラリ(アプリ同梱の静的アセット、Storageではない)
type ReferenceImage = {
  id: string;
  category: PhotoAssessment['results'][number]['improvements'][number]['category'];
  asset: ImageSource;    // require()されたバンドル内イラスト
  caption: string;       // 「明るい窓際で、斜め45度から」等の言語ガイド
};
```

- プロキシへ送信するデータ: 写真のバイナリ(判定時)/スクショまたはテキスト(返信支援時)のみ。ユーザー識別子は送らない(匿名)。プロキシは結果を返すのみで保存しない。
- PostHogへ送るイベントにも写真・会話内容は含めない(イベント名とメタ情報のみ)。

## 8. 画面構成

| # | 画面 | 主な要素 |
|---|---|---|
| S-1 | オンボーディング | 価値説明(3枚以内)+18歳以上確認(確認しないと先へ進めない)。価値説明には差別化コピー2点を必須要素として含める: (a)「なぜこの写真が良いか、根拠を示します」(理由付き判定)、(b)「実在の人物に似せた画像は作りません。信頼できるアドバイスだけを届けます」(写真詐欺の助長回避)(AC-021) |
| S-2 | ホーム | 2大CTA「写真をみてもらう」「返信を考えてもらう」+残り無料回数表示+履歴導線 |
| S-3 | 写真選択 | 端末ライブラリから1〜5枚選択 → 送信。**前提条件: フォトライブラリ権限状態(未リクエスト/許可/限定/拒否)により分岐** — 未リクエスト時はOS権限ダイアログを表示。拒否時は「写真へのアクセスが許可されていません」説明画面+「設定を開く」ボタン(iOS設定のアプリ設定ページへ誘導)を表示し機能は実行させない。限定時は選択済み写真の範囲で利用可+「他の写真も追加で選べます」案内。許可時は通常動作(AC-018) |
| S-4 | 判定中 | 進行インジケータ(30秒目安の文言)。タイムアウト時はエラー+再試行 |
| S-5 | 判定結果 | 推奨メイン写真+各写真のスコア・理由・改善提案。改善提案ごとに「参考イメージを見る」導線。モデレーション・人物検出により判定対象から除外された写真がある場合はその旨を表示する(AC-022・AC-024) |
| S-6 | 参考イメージ | カテゴリ対応の静的イラスト+言語ガイド(撮り方の説明) |
| S-7 | 返信支援入力 | スクショ選択 or テキスト貼り付けのタブ切替+トーン選択。**前提条件: スクショタブはS-3と同じ権限状態(未リクエスト/許可/限定/拒否)により分岐**(挙動はS-3と同一)。権限拒否時もテキスト貼り付けタブは利用可能とする(AC-019) |
| S-8 | 返信案結果 | 返信案3件(コピー ボタン付き)+各案の狙い |
| S-9 | 履歴 | 過去の判定・返信セッション一覧 → 詳細再表示(オフライン可) |
| S-10 | ペイウォール | 無料枠超過時・設定から表示。価格・特典・購入・リストア |
| S-11 | 設定 | サブスク管理・リストア、プライバシーポリシー、利用規約、ライセンス表記、データ削除 |

ナビゲーション: S-2をルートとするスタック構成。UIの詳細方針はSTEP 2.5(ui-direction.md)で確定する。

## 9. 受け入れ条件(AC)

判定不能な表現(「使いやすい」「適切に」等)は使用しない。各ACは対応する自動テストを持つこと(テストのないACは完了扱いにしない)。

---

**AC-001 写真判定の基本フロー** — Must / E2E(Maestro)
- 前提データ: 18歳確認済み、無料枠残あり、端末ライブラリにテスト画像3枚、ネットワーク接続あり、**フォトライブラリ権限「すべて許可」済み**(権限状態ごとの分岐はAC-018で検証)、送信画像はモデレーション「問題なし」判定(不適切判定時の挙動はAC-022で検証)、画像には人物が検出される(人物検出失敗時の挙動はAC-024で検証)。バッチ内の一部の写真のみがモデレーションNG・人物検出失敗となるケースの挙動はAC-022・AC-024で定義する(decision-log.md DL-006)
- Given: ホーム画面を表示している
- When: 「写真をみてもらう」→写真3枚を選択→送信する
- Then: 判定結果画面に (a) 推奨メイン写真が1枚明示され、(b) 3枚それぞれにスコア(1〜5)と理由が1件以上と改善提案が1件以上表示される
- 失敗時: (a)判定結果のいずれかの要素が欠けたレスポンス(モデレーション・人物検出により正当に除外された写真は含まない。除外の扱いはAC-022・AC-024を参照)の場合、部分表示せずエラー画面+再試行ボタンを表示する。(b)写真選択(S-3)で0枚選択、または6枚以上選択しようとした場合は送信ボタンを無効化(または6枚目以降の選択操作自体を無効化)し、「1〜5枚を選択してください」という説明を表示する(APIは呼ばない)

**AC-002 判定の応答時間とタイムアウト** — Must / integration(Jest+モック)
- 前提データ: プロキシ応答を遅延させられるモック環境
- Given: 写真を送信済みで判定中画面を表示している
- When: 60秒以内に応答が返らない
- Then: リクエストを中断し、タイムアウトエラーと再試行ボタンを表示する。再試行時は無料枠を追加消費しない
- 失敗時: 中断できない場合もUIはエラー表示に遷移し、以降の応答は破棄する
- 補足: 30秒以内の結果表示を性能目標とし、実機スモーク(手動)で通常回線での実測を記録する

**AC-003 判定結果の表現ルール(出典誤認防止)** — Must / unit(Jest)
- 前提データ: 表現検証関数と禁止パターンリスト(「Pairsのデータ」「Tinderの統計」等、他社名+データ/統計を想起させるパターン)
- Given: AIから判定結果テキストを受信した
- When: 表現検証関数に通す
- Then: 禁止パターンを含む場合は該当文を除去または再生成し、画面には禁止パターンを含むテキストを一切表示しない
- 失敗時: 再生成が2回失敗した場合はその項目を「改善提案を生成できませんでした」に置換して表示する

**AC-004 フィードバック文言の禁止表現フィルタ** — Must / unit(Jest)

**AC-022 アップロード画像のコンテンツモデレーション** — Must / integration(Jest+モック)
- 前提データ: モデレーション判定結果を(写真1枚ごとに)切り替えられるモック環境、無料枠残あり
- Given: 写真判定(S-3、1〜5枚のバッチ)またはスクショ返信支援(S-7、常に1枚)で画像を選択し送信した
- When: 判定・返信生成パイプラインが実行される
- Then: **vision AI APIへの送信前に**、送信された画像ごとにコンテンツモデレーションチェックが実行される。
  - **S-7(返信支援、1枚)**: 「不適切」と判定された場合は返信案生成を行わず、ガイドライン違反である旨の画面を表示し、無料枠を消費しない。「問題なし」の場合のみvision APIへ送信し通常フロー(AC-006)に進む
  - **S-3(写真判定、1〜5枚のバッチ)**: 「不適切」と判定された写真のみをそのバッチの判定対象から除外し、除外されなかった残りの写真でAC-001の通常フローを続行する。除外の結果、**判定対象の写真が1枚も残らなかった場合**はガイドライン違反である旨の画面を表示し、無料枠を消費しない。**1枚以上が判定対象として残った場合**は通常どおり判定結果を表示し、無料枠は1回分のみ消費する(AC-009補足)。この場合、判定結果画面(S-5)に除外があったことを示す表示を行う(decision-log.md DL-006)

- 補足: プロキシ入口では本ACのモデレーションチェックより先にレート制限チェック(AC-023)が行われる。レート制限超過時はモデレーションチェックにも進まず、AC-023のエラー表示となる。S-3のバッチ内一部除外はAC-001の「レスポンス要素欠落エラー」とは別ケースであり、AC-001の失敗時記述の対象外とする
- テスト明記: integration(Jest+モック)で「S-7で不適切判定時にvision API呼び出しが発生しないこと」「S-3で一部の写真のみ不適切判定の場合に該当写真を除外して残りが判定されること」「S-3で全滅した場合にvision API呼び出しが発生せず無料枠が消費されないこと」「S-3で一部除外時は無料枠が1回分のみ消費されること」「S-7で問題なし判定時のみ通常フローに進むこと」「チェックエラー時に送信されないこと」を検証

**AC-023 プロキシのレート制限(不正利用・コスト超過対策)** — Must / integration(Jest+モック)
- 前提データ: プロキシのレート制限閾値・カウンタを任意に設定できるモック環境
- Given: 同一IPアドレスからのリクエストが送信されている
- When: レート制限閾値(1時間あたり20回、24時間あたり100回のいずれか)を超過するリクエストがプロキシに到達する
- Then: プロキシはHTTP 429を返しvision APIを呼び出さない。クライアントは「アクセスが集中しています。しばらくしてから再度お試しください」という専用エラー画面を表示し、無料枠を消費しない
- 失敗時: レート制限機構自体が利用不能な場合はfail-open(制限なしで通す)にせず、通信エラーと同じ扱いで拒否する(fail-closed)
- 補足: レート制限はIPアドレス単位であり、同一IP配下の複数端末(公衆Wi-Fi・オフィス等)の正規利用を誤ってブロックしうる残存リスクをdecision-log.md DL-004に記録済み。デバイス単位の恒久対策(DeviceCheck/App Attest等)はv1.0スコープ外
- テスト明記: integration(Jest+モック)でレート制限超過時に「vision API呼び出しが発生しないこと」「無料枠が消費されないこと」「専用エラーメッセージが表示されること」「機構エラー時もfail-closedとなること」を検証

**AC-024 写真判定における人物検出失敗時のフォールバック** — Must / integration(Jest+モック)
- 前提データ: 1〜5枚のバッチのうち一部または全部が人物の写っていない画像(風景・物のみ等)、無料枠残あり
- Given: 写真選択(S-3)から、人物が写っていない画像を含むバッチを送信した
- When: AIが該当画像について人物を検出できない旨のレスポンスを返す
- Then: 人物が検出できなかった写真のみをそのバッチの判定対象から除外し、除外されなかった残りの写真でAC-001の通常フローを続行する。除外の結果、**判定対象の写真が1枚も残らなかった場合**は「人物が写っている写真を選んでください」という説明とともに写真選択画面へ戻る導線を表示し、無料枠を消費しない。**1枚以上が判定対象として残った場合**は通常どおり判定結果を表示し、無料枠は1回分のみ消費する(AC-009補足)。この場合、判定結果画面(S-5)に除外があったことを示す表示を行う(例:「◯枚の写真は人物を検出できず、判定対象から除外されました」。文言はAC-022と共通化してよい。decision-log.md DL-006)
- 失敗時: 検出不能のままAIがスコア・理由等の判定結果を生成してしまうことを防ぐため、プロンプトで「人物を検出できない場合は指定のエラー形式で返す」ことを指示し、そのパース処理をunitテストする。全滅ケース・一部除外ケースいずれも、AC-001の「レスポンス要素欠落エラー」とは別ケースであり、AC-001の失敗時記述の対象外とする
- テスト明記: integration(Jest+モック)で「一部の写真のみ人物検出失敗の場合に該当写真を除外して残りが判定されること」「全滅した場合に判定結果が表示されず無料枠が消費されないこと」「一部除外時は無料枠が1回分のみ消費されること」「指定エラー形式のパースが正しく機能すること」を検証

## 10. リリース Definition of Done

以下をすべて満たした時点でリリース可とする。判定はrelease-checklist.mdに記録する。

1. **AC全件Pass**: AC-001〜024のうちMust全件がPass。Should(AC-005, 012, 016)は未達の場合、既知不具合として記録し人間の承認を得る
2. **必須自動テストPass**: Jest(unit/integration)とMaestro(E2E)のスイートがCIまたはローカルで全件グリーン
3. **実機スモークPass**: 実機(iOS)で フローA(写真判定→参考イメージ)・フローB(返信支援)・フローC(購入→リストア)を通しで実行し、AC-002の応答時間実測値を記録
4. **クラッシュなし**: 実機スモーク中のクラッシュ0件。Sentry疎通確認済み(AC-017)
5. **プライバシー申告との整合**: App Storeプライバシー表示(データ収集: 写真・メッセージ内容は「収集しない」=送信のみで非保存、計測イベントは収集内容を正確に申告)とAC-014・015の実装が一致していることを確認。**プライバシーポリシーには、写真・メッセージ内容を判定・生成の目的で第三者AIサービス(vision LLM API)へ送信すること、および送信後は保存しないことを明記する**。**また、会話スクリーンショットには相手方(マッチング相手)の氏名・写真等の第三者情報が含まれる場合があり、これも返信案生成の目的でのみ第三者AIサービスへ送信し、送信後は保存しないことを明記する(decision-log.md DL-007)**
6. **審査用情報完備**: 審査メモ(プロキシの役割説明、年齢確認の説明、参考イメージが実在の顔を再現しない旨、**機能面の差別化ポイント〔理由提示の具体性・出典誤認防止の表現ルール(AC-003)・静的参考イラストによる撮影ガイド(F-2)〕**、**ATT不要の根拠〔匿名ID使用・IDFA不使用、AC-015〕**)、デモ手順、スクリーンショット、サポートURL、プライバシーポリシーURLが揃っている
7. **ライセンス確認済み**: 使用ライブラリのライセンス一覧を生成し、設定画面(S-11)から閲覧可能。同梱する参考イラストの権利(自作または商用利用可ライセンス)を確認済み
8. **既知不具合の記録・承認**: 未修正の不具合・未達Shouldをdecision-log.mdに列挙し、人間の承認を得ている
